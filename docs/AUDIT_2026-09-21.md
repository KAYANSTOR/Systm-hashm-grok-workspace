# تقرير التدقيق الشامل — نظام معمل هاشم الأحمدي

**التاريخ:** 21 سبتمبر 2026
**النطاق:** المحاسبة والقيود، دفتر المخزون، المزامنة، دوال الخادم، الهجرات، الواجهة المالية.
**الطريقة:** قراءة الكود سطرًا بسطر في الطبقات الحرجة، ثم **إثبات ميكانيكي** للثوابت المحاسبية عبر `npm run check:accounting` (يبني مخطط قاعدة البيانات فعليًا من `migrations/*.sql` في PGlite ثم يتحقق من 18 ثابتًا).

## 1. المشاكل الحرجة (أُصلحت في هذه الجلسة)

### 1.1 المبلغ المدفوع كان يُهمَل في ذمة الطرف — خطأ محاسبي مؤثر

**الخطورة:** حرجة (أرقام العملاء والموردين خاطئة، وازدواج في عرض الذمم).

**الأعراض:** فاتورة بيع نقدية بإجمالي 1000 ومدفوعة 1000:
- لحظة الحفظ يظهر رصيد العميل = 0 (صحيح، لأن `applyInvoiceEffects` تحسب الإجمالي − المدفوع).
- بعد أي تحديث للبيانات من الخادم يعود رصيد العميل = **1000** (خطأ) لأن الرصيد يُشتق من دفتر القيود.

**السبب الجذري:** كان يُكتب للفاتورة المعتمدة قيدان فقط:
1. `_party` → ذمم مدينة/دائنة بإجمالي الفاتورة.
2. `_pay` → الصندوق بالمبلغ المدفوع.
ولم يكن هناك قيد يقابل المدفوع **على حساب الذمة نفسه**، فلا يُقاصّ المدفوع من الذمة أبدًا. (مصدر الرصيد في الواجهة: `src/lib/store.ts` — مجموع القيود لكل مستند، وحساب الصندوق مستثنى من أثر الذمة.)

**الإصلاح:**
- ملف جديد كمصدر حقيقة واحد: `src/domain/invoice-ledger-rows.ts` يبني القيود الثلاثة لكل فاتورة معتمدة.
- `server/repository.ts`: `saveInvoice` و`syncLegacyData` صارا يستخدمان نفس الدالة (بدل كتابة SQL مكرّرة يدويًا في مكانين).
- `migrations/0024_invoice_balance_settlement.sql`: تُصلح **الفواتير القديمة** في قاعدة الإنتاج بإضافة قيد التسوية المفقود، بشرط `is_approved = true` و`paid_amount > 0`، وبقابلية إعادة تنفيذ آمنة.

**الإثبات:** `npm run check:accounting`
```
✅ فاتورة بيع نقدية مدفوعة كاملًا: رصيد العميل → 0
✅ فاتورة بيع مدفوعة جزئيًا: رصيد العميل = المتبقي
✅ مشتريات مدفوعة جزئيًا: رصيد المورد = المتبقي (دائن)
✅ هجرة 0024: الرصيد بعد الإصلاح = المتبقي فقط
✅ هجرة 0024: لا تكرار بعد ثلاث مرات
```

### 1.2 سلسلة الهجرات كانت تتعطل — تعذّر بناء قاعدة بيانات من الصفر

**الخطورة:** حرجة تشغيليًا (لا يمكن إنشاء بيئة جديدة ولا تطبيق خطة رجوع/استعادة).

**السبب الجذري:** الهجرة `0019_supabase_security_hardening.sql` تحوي:
- `revoke ... from anon, authenticated` → يفشل على أي Postgres لا يحتوي دورَي Supabase: `role "anon" does not exist`.
- `alter function public.bump_sync_version() ...` → **الدالة غير مُنشأة في أي هجرة موجودة** (يُرجّح أنها كانت في الهجرة المفقودة `0009`) → `function public.bump_sync_version() does not exist`.

النتيجة: على أي قاعدة جديدة تتوقف السلسلة عند 0019، فلا تُطبَّق 0020–0024 إطلاقًا.

**الإصلاح (**`migrations/0019_...`**):** سحب الصلاحيات محصور بوجود الدورين، وضبط `search_path` يمر على الدوال الموجودة فعلًا فقط (`to_regprocedure`). الأثر على Supabase كما هو تمامًا.

**الإثبات:** `npm run check:accounting` يبني المخطط كاملًا: `🧱 طُبِّقت 23 هجرة على PGlite بنجاح`.

**مطلوب منك:** تأكيد أي الهجرات مُطبَّقة فعلًا على قاعدة الإنتاج (الاستعلام في نهاية هذا الملف).

### 1.3 قيود الفاتورة المكرّرة في ملفين متباعدين

`src/lib/accounting.ts` كان يحوي نسخة ثانية كاملة من قواعد المحاسبة (`applyInvoice`، `applyVoucher`، `applyExpense`) **لا يستوردها ولا ينفّذها أي كود**، وهي متباعدة جزئيًا عن النسخة الحيّة في `src/domain/operations.ts` (مثال: ترقيم المصروفات). هذا هو بالضبط ما سمح بحدوث الخطأ 1.1 في مكان دون الآخر.

**الإصلاح:** حُذفت النسخة الميتة، وبقي `cashBalance` فقط مع شرح معماري يمنع تكرارها. (تراجعت تحذيرات lint من 36 إلى 32).

### 1.4 فقدان معلومات المستند عند إعادة الجلب من الخادم

**الخطورة:** متوسطة (تظهر في الصندوق والتقارير).

**الأعراض بعد كل تحديث من الخادم:**
- كل الحركات تُعرض بطريقة دفع «نقدي» لأن `payment_method` غير محفوظ في `financial_transactions` (العمود غير موجود أصلًا في الجدول).
- رقم المستند المعروض كان هو المعرّف الداخلي (`inv_ab12…`) لا رقم الفاتورة/السند.
- نوع المستند كان يُستنتج من **أول صف يُجلب** للمستند؛ فوجود صف السداد (`invoice_payment`) أولًا كان يجعل الفاتورة تُصنَّف «مصروفًا».

**الإصلاح في `src/lib/store.ts`:** طريقة الدفع ورقم المستند يُشتقّان من جدول المستند (فواتير/سندات/مصروفات)، ونوع المستند والبيان والرقم تُؤخذ من صف المستند الأصلي (`_party`) لا من صف السداد، وتُصنَّف `invoice_payment` كفاتورة.

## 3. ثوابت محاسبية مفحوصة (تُشغَّل بأمر واحد)

| الثابت | الحالة |
|---|---|
| بيع نقدي مدفوع كاملًا → ذمة العميل صفر | ✅ |
| بيع آجل → ذمة العميل = الإجمالي، والصندوق لا يتأثر | ✅ |
| بيع مدفوع جزئيًا → الذمة = المتبقي فقط | ✅ |
| شراء مدفوع جزئيًا → ذمة المورد = المتبقي | ✅ |
| سند قبض → الصندوق +المبلغ، ذمة العميل −المبلغ | ✅ |
| سند صرف → الصندوق −المبلغ، ذمة المورد −المبلغ | ✅ |
| حذف/إلغاء مستند → تصفير أثره على الذمة والصندوق | ✅ |
| هجرة الإصلاح آمنة لإعادة التنفيذ (لا تكرار) | ✅ |

**التشغيل:** `npm run check:accounting` (18 فحصًا، يبني قاعدة بيانات كاملة من الصفر).

## 4. استعلام تحقّق مطلوب على قاعدة الإنتاج

لمعرفة أي الهجرات مُطبَّقة فعلًا (لأن السلسلة كانت تتعطل عند 0019 في أي بيئة جديدة):

```sql
select name, applied_at from public._migrations order by name;
```

- ظهور `0020` حتى `0024` يعني أن السلسلة سليمة.
- غياب `0024` طبيعي قبل هذا النشر — بعد النشر يجب أن تظهر.
- أي غياب لـ `0020`–`0023` يعني أن جداول/فهارس ناقصة في الإنتاج (فهارس، حالة حساب الموظف، الهويات الموحّدة للهاتف، رموز الاسترداد) ويجب إعادة تشغيلها.

## 5. خلاصة

- **أُصلحت 4 مشاكل** (واحدة منها محاسبية حرجة تُغيّر أرقام ذمم العملاء والموردين، وواحدة تمنع بناء قاعدة من الصفر).

- صار في المشروع **فحص محاسبي قابل للتشغيل** يُمنع به رجوع أي من هذه الأخطاء مستقبلًا.
