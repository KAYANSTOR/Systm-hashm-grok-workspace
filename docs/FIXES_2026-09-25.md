## 1. 🐞 تصفية قاعدة البيانات كانت تفشل صامتة (الأخطر — أُصلح)

**شكوى صاحب المشروع:** «عندما أفعّل حذف وتصفية قاعدة البيانات لا يتم حذف وتصفية قاعدة البيانات الذي في السحابة ولا الذي في الجهاز.»

**السبب الجذري:** في `src/server/repository.ts` كانت دالة `resetDatabase` تحذف جداول **اختيارية** داخل `try/catch`، ومنها آخر سطر:

```ts
try { await tx`delete from audit_events`; } catch { /* optional */ }
```

وجدول `audit_events` **محمي بمُشغِّل `audit_events_append_only`** (الهجرة `0012_audit_append_only.sql`) يرفض أي `DELETE` **دائمًا**:

```sql
create trigger audit_events_append_only
before update or delete on audit_events
for each row execute function prevent_audit_event_mutation();
```

في PostgreSQL، أول جملة تفشل داخل معاملة تُدخلها في حالة **aborted**: كل الجمل التالية تُتجاهل، و`COMMIT` على معاملة مُجهَضة يتحول إلى `ROLLBACK` **ويُبلِّغ عن النجاح**. لذلك:

- الخادم أعلن `{ status: "ok", cleared: true }` بينما **لم يُحذف أي صف** (كان `audit_events` آخر جملة حذف، فكل ما قبلها أُجهِض في اللفة النهائية).
- الواجهة عرضت «تم حذف وتصفية بيانات العمل بنجاح».
- لأن الواجهة تتبع التصفية بإعادة قراءة البيانات من الخادم (`fetchFromDb`)، عادت البيانات كما هي — فبدا أن بيانات **الجهاز أيضًا** لم تُحذف.

**الإصلاح:**

1. وحدة جديدة `src/domain/purge.ts` — منطق تصفية واحد تستخدمه الواجهة الخادمية والفحص الآلي:
   - `PURGE_TABLES` بترتيب يحترم المفاتيح الأجنبية.
   - لا `try/catch` حول أي حذف إطلاقًا.
   - وجود الجداول يُفحص **قبل** الحذف عبر `information_schema` (استعلام ناجح)، لا بمحاولة حذف تفشل.
   - بعد الحذف **يتحقق** بجملة `count(*)` لكل جدول، ويرمي خطأً إن بقي أي صف — فلا نجاح كاذب بعد اليوم.
2. `audit_events` **لم يعد يُحذف أبدًا** — بتصميم النظام (سجل تدقيق غير قابل للتعديل). وبدلًا من حذفه، صار `resetDatabase` **يكتب فيه حدث `purge`** يوثّق من نفّذ التصفية ومتى. ولهذا الجدول فائدة حقيقية الآن بدل أن يكون سببًا لعطل.
3. `npm run check:purge` — فحص آلي جديد يبني المخطط في PGlite ويُثبت العلة والإصلاح.

**الأدلة (تشغيل فعلي):**

```
🔎 محاكاة السلوك القديم: invoices=1 · parties=2 · استثناء=لا
✅ العلة القديمة مُعاد إنتاجها: البيانات تبقى كاملة رغم نجاح المعاملة
✅ أُفرِغ جدول financial_transactions … invoices … vouchers … parties … (١٢ جدولًا)
✅ سجل التدقيق محفوظ ولم يُحذف (بتصميم النظام) → 1 → 1
✅ يفشل بصراحة ويُجهِض التصفية عند تعذّر الحذف (لا نجاح كاذب)
```

وفحص شامل بمتصفح حقيقي على التدفق كاملًا (`scripts/purge-e2e.mjs`):

```
✅ إنشاء عميل جديد من شاشة العملاء
✅ العميل وصل إلى قاعدة البيانات (ظهر بعد إعادة التحميل من الخادم)
✅ التصفية أبلغت عن النجاح
✅ بيانات الخادم فُرِّغت فعلًا (مرات الظهور بعد التصفية: 0)
```

## 3. حذف حقول لم يطلبها صاحب المعمل

بطلب صريح: أُزيلت من شاشة الإعدادات حقول **البريد الإلكتروني** و**السجل التجاري** و**الرقم الضريبي**. بقيت بيانات المعمل: الاسم، الشعار، العنوان، الهاتف، الموقع الإلكتروني، ونص التذييل. أسماء الحقول بقيت في قاعدة البيانات وفي قوالب الطباعة (التي تُخفيها تلقائيًا عند غيابها)، فحذفها من الواجهة لا يكسر أي مستند أو هجرة.

## 5. ملاحظة للأجيال القادمة

- **لا تُضِف `try/catch` حول أي حذف داخل معاملة.** جملة فاشلة واحدة تُلغي المعاملة كلها وتُخفي النتيجة، و`COMMIT` يبدو ناجحًا.
- أفعال الحذف/التصفية يجب أن تنتهي بـ**تحقق** (`count = 0`) لا بمجرد تنفيذ `delete`.
- HMR معطّل في هذه البيئة: بعد أي تعديل، شغّل `freebuff-preview restart` قبل التحقق بمتصفح، وإلا فحصت نسخة قديمة.
