# تقرير تدقيق أداء التنقل — نظام هاشم

## ROOT CAUSES

1. **التقسيم كان موجودًا جزئيًا لكنه غير مُعلن صراحةً في إعدادات TanStack Start.** تحليل build الحالي أظهر أن الصفحات تُنتج chunks منفصلة بالفعل، لكن إعداد `autoCodeSplitting` غير موجود في `tanstackStart`. هذا يجعل السلوك معتمدًا على تحويلات ضمنية ويصعّب ضمان عدم عودة الصفحات الثقيلة إلى الحزمة الأولية. الحزمة الأولية الحالية تقارب 539 KB قبل الضغط، بينما chunk التقارير يقارب 374 KB وchunk PDF يقارب 399 KB.

2. **مرحلة تهيئة البيانات تنفذ حسابًا تربيعيًا عند تحميل قاعدة البيانات.** في `src/lib/store.ts` يتم حساب رصيد كل عميل/مورد عبر `transactions.filter(...)` داخل `map(...)`. مع `P` أطراف و`T` معاملات، هذا يساوي تقريبًا `O(P×T)` ويحتجز الـmain thread أثناء أول جلب، وهو سبب مباشر محتمل لإحساس التجمّد بعد فتح التطبيق أو بعد مزامنة البيانات.

3. **الجلب الأولي يقرأ مجموعة بيانات كاملة دفعة واحدة.** `src/server/repository.ts:fetchAllData` يجلب كل الأطراف والمنتجات والفواتير وبنودها والسندات والمصروفات والمعاملات، حتى لو كانت الشاشة المطلوبة لا تحتاج إلا جزءًا منها. هذا لا يعيد الجلب عند كل route حاليًا، لكنه يجعل أول تهيئة ثقيلة ويخلط بين cache التطبيق ومصدر البيانات.

4. **المزامنة الخلفية مربوطة باشتراك عام في Zustand.** الاشتراك لا يسبب إعادة render مباشرًا لكل المكونات لأنه خارج React، لكنه يفحص المتجر كاملًا بعد كل `set` ويعيد جدولة مزامنة عامة لأي تغيير في arrays كبيرة. هذا يزيد ضغط العمل بعد العمليات المتتابعة، خصوصًا عندما تقوم المحاسبة بتعديل عدة collections معًا.

5. **الصفحات الثقيلة تستخدم بيانات المتجر كاملة عند فتحها.** التقارير تعتمد على invoices/customers/suppliers/transactions/inventory/expenses كلها وتنفذ اشتقاقات كبيرة في render. هذا مقبول بعد فصل route chunk، لكنه يظل تكلفة فتح الشاشة الأولى؛ لذلك يجب ألا يدخل initial bundle، مع إبقاء الحسابات محلية ومُحسنة بدل إعادة تصميم منطق الأعمال.

6. **لا توجد Firebase/Firestore listeners في المسار التنفيذي الحالي.** إعداد Firebase موجود، لكن عمليات البيانات الفعلية تمر عبر server functions وPGLite/Postgres في `src/server/repository.ts`، ولا توجد `onSnapshot` أو listeners غير ملغاة. لذلك لا يوجد دليل على duplicate listener كسبب للمشكلة.

7. **الاختبارات المطلوبة لبعض المسارات لا يمكن تنفيذها حرفيًا لأن المستودع لا يحتوي routes للمشتريات أو الموظفين.** المسارات الموجودة هي: الرئيسية، المبيعات، المخزن، السندات، الصندوق، المصروفات، التقارير، الأطراف، والإعدادات.

## FIX PLAN

1. تفعيل `autoCodeSplitting` صراحةً في إعداد TanStack Start، مع إبقاء مكونات route غير مُصدّرة حتى يستمر فصلها تلقائيًا.
2. إضافة preload intent الموجود في روابط الواجهة إلى كل روابط التنقل المهمة، مع انتقال UI قصير لا ينتظر خروج الصفحة.
3. إصلاح حساب أرصدة الأطراف باستخدام تجميع واحد `Map` بدل `filter` المتكرر، مع الحفاظ على النتائج نفسها.
4. إضافة حارس جلب واحد (in-flight guard) وcache زمني قصير لعدم تشغيل طلبين متزامنين أثناء التهيئة/العودة online.
5. تقليل عمل اشتراك المزامنة عبر جدولة واحدة قابلة للإلغاء وعدم بدء مزامنة جديدة إذا كانت مزامنة سابقة قيد التنفيذ.
6. إعادة تحليل production bundle وتشغيل typecheck/lint/tests/build بعد التعديل، ثم مراجعة diff قبل الدفع.

## معيار القبول

- يبدأ route transition فورًا ولا توجد فترة فراغ بسبب `AnimatePresence mode="wait"`.
- كل صفحة غير حرجة تبقى في chunk مستقل ولا تدخل تقارير/PDF الحزمة الأولية.
- لا يوجد حساب `filter` للمعاملات داخل دورة الأطراف عند تهيئة البيانات.
- لا توجد طلبات تهيئة متزامنة أو مزامنة عامة متراكمة.
- لا تتغير RTL أو الصلاحيات أو منطق المحاسبة أو السلوك offline.

## نتائج التنفيذ

تم تفعيل `autoCodeSplitting` صراحةً في إعداد TanStack Start. كما تم تحسين تهيئة Zustand بتجميع أرصدة الأطراف في مرور واحد، وإضافة حارس يمنع الجلب المتزامن خلال 15 ثانية، وحارس وعد واحد يمنع تداخل عمليات المزامنة. تمت إضافة استثناء لملفات `patch_store*.ts` القديمة غير التنفيذية، لأنها تحتوي نصوص patch غير صالحة للتحليل وليست جزءًا من runtime.

فحص الإنتاج النهائي نجح. حجم الحزمة الأولية للعميل بلغ **538,809 bytes**، بينما بقيت التقارير في chunk مستقل بحجم **374,383 bytes**، وPDF في chunks مستقلة (JS PDF: **399,057 bytes** وhtml2canvas: **199,496 bytes**) ولا تظهر داخل الحزمة الأولية. `typecheck` نجح، وجميع **45 اختبارًا** نجحت، و`lint` نجح دون أخطاء مع **30 تحذيرًا قديمًا** من unused variables في ملفات موجودة مسبقًا.
